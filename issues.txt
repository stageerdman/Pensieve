LARGE-MEDIA-SYNC — SHIPPED to main (2026-10-20, native app rebuilt+installed):
- [x] Root cause of both items below: the whole-file-as-one-base64-string PUT/GET path
      (adapter.ts uploadMedia/downloadMedia) had no real ceiling on how long it could run or
      how big the JS string could get — for a large file this could block the renderer's JS
      thread for a long time and/or exceed Graph's real 4MB simple-upload cap, which is exactly
      why sync could get stuck showing "Backing up…"/"Backing up 1 image…" forever with no
      failure ever surfacing.
- [x] The 78 MB audio recording (mvdrv6gg-zqr40w/mvdululy-rr0bjfyk.m4a) and anything else past
      4 MiB now routes through a resumable Graph upload session (uploads) or chunked Range GETs
      to a .part file (downloads) — both streamed straight from/to disk in Rust
      (media_transfer.rs), never materialized as one JS string. Resume after an app close is
      automatic: Graph tracks how many bytes a session actually received server-side, so the
      next sync just asks and continues from there — no local per-chunk bookkeeping needed.
      Bounded per-chunk timeout+retry means a stalled chunk fails (and resumes) in ~2 minutes
      instead of hanging the sync forever. See updates/2026-10-20 LARGE-MEDIA-SYNC - OPEN/.
- [ ] Not done: no explicit "pause" UI — closing the app IS the pause, by design (mirrors the
      transcription-resume precedent). If the owner wants a visible "N% backed up, paused"
      affordance instead of just the quiet whisper, that's a follow-up, not a bug.

TRANSCRIPTION-RESUME — shipped to main 2026-10-19 (owner to device-confirm):
- [x] Stop + restore: an interrupted transcription (quit/crash/error/cancel) now resumes on reopen.
      czech-whisper checkpoints per VAD chunk to <appData>/transcription/<ref>.partial.json and
      resumes mid-file; Pause actually kills the running engine child (cancel_transcription) and keeps
      the checkpoint so Run resumes; queue state (model/order/playing/mode) persists to localStorage
      and auto-resumes on launch. Parakeet is single-shot (restarts whole, ~3 min). Folder OPEN.
- [x] ACTUAL root cause of "engine exited with 120" FOUND + FIXED (2026-10-19, 3-agent debug team,
      reproduced end-to-end): it was a RUST PANIC, not the engine. transcribe.rs did
      `tail.split_off(tail.len()-2000)` on the stderr tail; split_off panics off a UTF-8 char
      boundary, which mlx_whisper's tqdm `█` (3-byte) bars trigger → stderr-reader thread dies →
      child stderr pipe closes → engine's next stderr write → BrokenPipeError → CPython exit 120,
      empty stdout (hence the empty popover tail, and why os._exit/ENGINE ERROR/retry were all
      bypassed; CLI/TTY never hit it). Fix: byte-safe bounded line buffer (push_bounded, +regression
      tests) reading raw bytes+lossy; verbose=None kills the tqdm flood; _safe_stderr guards every
      engine stderr write; exit code-vs-signal reporting; --debug-log on disk; env hardening +
      caffeinate -w child (App Nap/sleep can invalidate Metal on a ~2h job). The earlier os._exit /
      ENGINE-ERROR-wrap / per-chunk-retry changes stay as defense-in-depth.
- [ ] Parakeet has no mid-file checkpoint (single library call) — restarts from 0 on resume.
- [ ] Auto-resume rides on the SyncStatus-mounted queue; if OneDrive is ever "unavailable" the queue
      doesn't mount, so resume would wait for a surface that mounts it. Fine for the connected owner.

- [x] "engine exited with status 120" FIXED (2026-10-19): Python returns 120 when a shutdown-time
      stream flush fails (MLX/thread/claude-p cleanup disturbing the inherited stdout pipe) AFTER the
      full transcript was already written — the Rust shell was discarding a good result. Fix: engine
      flushes then os._exit(rc) to skip CPython finalization; Rust now trusts non-empty stdout (one
      json.dump at the end == completed) regardless of exit status, parseTranscript validates.
- [x] Error icon tooltip was a native `title` — dead in WKWebView. Replaced with a real portaled
      popover (ErrorTip, z-70, shows on hover + pins on click) so the reason is actually visible.
- [x] Transcription failures now show the reason on HOVER over the red error icon (2026-10-19):
      cleanEngineError strips JSON-progress/tqdm noise from the Rust stderr tail and keeps the
      real Python exception; threaded ProcessItem.errorMsg → ProcessRow tooltip. NB diagnosis:
      the engine itself works end-to-end on the 75-min "How to achieve Understanding" tape
      (parakeet ~3 min/953 segs; czech-whisper is just SLOW — ~101s per 60s of audio, so the
      Czech default on a 75-min file is ~2 h + polish). Logger is in-memory only, so a past
      failure's reason was unrecoverable — the hover is now the way to see it next time.
- [ ] Per-row model menu can clip at the bottom of a long queue — portal it.
- [ ] Packaging: engine runs via the transcriber venv (/Users/stage/dev/transcriber/.venv, or
      $PENSIEVE_PYTHON); bundling a self-contained Python+MLX runtime into the .app is deferred.
- [ ] Czech on a 75-min tape ~25-30 min (Parakeet ~2 min) — no in-UI ETA; acceptable for now.
