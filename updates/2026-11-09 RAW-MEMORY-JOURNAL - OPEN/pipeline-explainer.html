How the Raw Memory pipeline actually works

You're right to call out my last report — "works entirely on one device" was a confusing way to put it, and worth correcting properly rather than just softening the wording. Here's exactly what runs where, with the real commands and the real test case.

Correcting the confusion

AI never runs on the phone. There is no AI on iPhone, full stop — that's not new, it's the project's standing rule (CLAUDE.md: "AI is a desktop-only capability... not on mobile"), and everything I built respects it. The Journal spell on the phone does zero AI — it just takes photos and stores them locally.

What I actually meant by "works on one device," stated honestly: I unit-tested the desktop-side orchestration logic (describe → split → write Memories) by constructing a fake Raw Memory directly in a test and feeding it to processRawBatch with a mocked AI response. That proves the logic is correct. It does not prove a real phone-captured batch can ever reach that logic — because nothing currently carries it from the phone to the desktop. That's the sync gap below, and it's not a minor missing extra: without it, the feature doesn't connect end to end at all yet.

The pipeline, stage by stage

Phone — built Capture Journal spell → live camera → pages stored in the phone's own IndexedDB + a small local list. No AI. No network.
→
⚠ Not built Sync Nothing currently moves a Raw Memory from the phone's storage to the desktop's. This is the missing link.
→
Desktop only — built AI processing Reads each page, detects dates, splits the batch, writes new Memories. Shells out to the logged-in claude CLI, locally, on the Mac.
→
Desktop — built Final Memory A normal note: a Journal block (photos) + searchable per-page transcripts.

Today, the first and third boxes both work in isolation and are both tested. There is no path between them. A batch shot on the phone sits on the phone, indefinitely, until sync is built.

The AI call — what actually happens, verified live

I didn't guess at this. I ran the real claude CLI myself, from the terminal, before writing any Rust code, to find out how it actually behaves headlessly.

1
Desktop finds a batch ready to processtested

The sync drawer's Process queue scans the desktop's own local vault for Raw Memory records with status synced. (Today, nothing ever puts one there except a developer test — see the gap above.)

2
For each page, a real subprocess callverified against the live binary

Rust spawns claude -p with the prompt piped over stdin — the exact pattern this project already uses elsewhere for transcript polishing, not a new invention.

$ echo 'Read the file /tmp/x.txt and reply with exactly its contents.' | claude -p I don't have permission to read that file — please grant access or paste its contents. $ echo 'Read the file /tmp/x.txt and reply with exactly its contents.' | claude -p --add-dir /tmp SECRET_MARKER_42

That first failure is why the Rust command grants --add-dir for exactly the one folder holding the page image being described — nothing wider.

$ claude -p "Reply with exactly OK." --output-format json --bare {"result":"Not logged in · Please run /login", ...}

--bare forces API-key-only auth and never reads the logged-in session — which is exactly the auth path Pensieve's whole AI design deliberately avoids (CLAUDE.md: "uses the logged-in Claude account, no API key"). So the real command never passes --bare, confirmed by watching it fail.

The actual prompt sent per page

Read the handwritten journal page image at this exact path: <absolute path>

Transcribe every legible word of handwriting on the page, in reading order. If a
word is genuinely illegible, skip just that word rather than refusing — only
leave the transcript empty if the page is truly blank.

Then look for a DATE HEADER the writer put on this page (e.g. "Nov 3",
"November 3rd", "Mon Nov 3", a date in any format). A page normally has at
most one NEW date header.

Respond with ONLY a single JSON object and nothing else:
{"transcript": "...", "dateHeader": "..." | null, "continuesPrevious": true|false}

This part is unverified in the sense that matters most: no real handwriting has gone through it yet. The mechanism (spawn, permissions, auth, JSON parsing) is proven; whether it transcribes your handwriting well is not.

The date-split algorithm — a worked example

This is the part that runs entirely in TypeScript, no AI inside it — it just groups whatever the AI call reported per page. Here's the actual test case from the test suite: 5 pages, one shared boundary.

p1Nov 3
p2(no header)
sharedp3Nov 4
p4Nov 5
p5(no header)
PageAI reportsWhy
p3dateHeader: "Nov 4", continuesPrevious: trueThe photo shows the tail of Nov 3's entry AND the Nov 4 header on the same page.
p4dateHeader: "Nov 5", continuesPrevious: falseA clean break — nothing of Nov 4 bleeds onto this page.

The algorithm's output — note p3 appears in two groups, not torn in half:

Nov 3
p1, p2, p3
Nov 4
p3
Nov 5
p4, p5

Downstream, p3's image file is physically copied twice — once into the Nov 3 Memory's own folder, once into the Nov 4 Memory's — because the Raw Memory's own folder gets deleted once processing finishes, so neither new Memory can keep pointing at it.

What's actually needed to make this reachable

In order, to go from "two working islands" to one real feature:

  1. Sync for the Raw Memory object kind — push from phone, pull on desktop, tombstone on delete. This is the piece I held off on, because it touches your live OneDrive account and I can't safely iterate on it without testing against the real thing.
  2. A real test batch — actual photographed pages, run through describe_journal_page for real, to see whether the prompt needs tuning.
  3. An on-device pass of the camera screen — iOS PWA camera behavior has surprised this project before.
